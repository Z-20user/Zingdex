# 授权机制与多端部署 · 完整复盘

> 写给两类人：想学「一个人怎么把软件做出来并分发给别人」的读者，
> 以及未来想重新捡起这个项目的自己。
>
> 记录时间：2026-11-02 · 适用版本：v0.0.1 – v2.1.3

---

## 零、一句话总结

这套授权机制做得不差，但它解决的是一个**当时并不成立的问题**：
在还没有用户的时候，先解决「怎么收费」。

多端部署这条线是走通的，而且留下了可复用的工程资产；
授权这条线是走通之后主动放弃的——这是判断，不是失败。

---

## 一、当初为什么要做授权

三个动机，按当时的真实优先级：

| 动机 | 说明 | 事后看 |
|---|---|---|
| 分发控制 | 不想让作品被随意转载、二次打包 | 合理，但纯前端挡不住 |
| 商业化准备 | 想着「以后要收费」，先把闸门装好 | 前提不成立：还没有用户 |
| 心理安全感 | 有个"正式产品"的样子 | 代价是首次体验变重 |

**关键误判**：把「收费能力」当成了「产品必需品」。
实际上收费是**结果**，不是**起点**。

## 二、授权机制是怎么搭起来的

### 2.1 分层模型

```
访客（未激活）
  └─ 普通等级 1–10      每日额度：第 1 级 100 次/天，每级 +300
       └─ S 级           1000 枚（S0001–S1000），不限次数
            └─ 管理员令牌  仅 Windows 安装版，会话级
```

- **等级**解决「用量」：给人升级的理由
- **S 级**解决「大客户」：一次给足，不再计数
- **令牌**解决「内部/开发」：临时管理员，退出即失效

### 2.2 密钥怎么发出去

| 渠道 | 形态 | 解决的问题 |
|---|---|---|
| 明文总表 | `用户密钥-10000枚.txt`、`S级激活码-1000枚.txt` | 母表，唯一真相 |
| 密钥 App | 安卓，指纹解锁，离线查看/领取 | 用户自助取码 |
| 离线密钥库 | Windows exe，主密码解锁，不联网 | 电脑端对账 |
| 客户端哈希表 | `keydata.js` | 应用内校验，不暴露明文 |

**设计意图**：母表在本地，客户端只拿哈希，两边对得上才放行。

### 2.3 校验怎么做的

演进过三代，每代都踩了坑：

| 代际 | 做法 | 结果 |
|---|---|---|
| 第一代 | 明文比对 | 一解包就露 |
| 第二代 | PBKDF2 + AES 加密随包 | 用户密钥显示为 0，故障率高 → 回退 |
| 第三代 | 哈希表 + 令牌 Ed25519 验签 | 能用，但见下 |

**第三代踩的坑（值得记住）**：

> Electron 33 自带的 Chromium **不支持 WebCrypto 的 Ed25519**。
> 网页层验签会直接报「当前 WebView 不支持 Ed25519」。
> 结论：桌面端一律交给主进程用 Node 的 `crypto` 验签，
> 网页层只作兜底。

另一个坑：令牌里带了「文件指纹」，每次发版都会变，导致升级后令牌失效。
后来改成「参考信息」而不是硬拦——**升级不该让用户重新授权**。

### 2.4 四端能力差异

| 端 | 1–10 级 | S 级 | 管理员令牌 |
|---|---|---|---|
| Windows 安装版 | 有 | 有 | 有 |
| Windows 便携版 | 有 | 有 | 无 |
| 安卓 | 有 | 有 | 无 |
| 网页 | 只读 | — | — |

差异本身是设计，不是 bug：**装到机器上的才配拿管理员**。

### 2.5 它到底挡住了什么

必须诚实：

| 威胁 | 挡得住吗 |
|---|---|
| 随手转发源文件 | 部分（需激活才能用） |
| 解包看内容 | **挡不住**，APK 里就是明文 |
| 改本地状态绕过 | **挡不住**，纯前端无服务端 |
| 二次打包分发 | 挡不住，只能靠法律与署名 |

**结论：纯前端授权，本质是"提高门槛"，不是"加密保护"。**

## 三、多端部署是怎么做的

### 3.1 四种形态，同一份内容

| 形态 | 体积 | 关键决策 |
|---|---|---|
| 网页站点 | 随源码 | 数据外部化，页面共用 |
| 安卓 APK | 2.7 MB | WebView 壳 + 本地资源 |
| Windows 便携版 | 290 MB | 整目录，不写注册表 |
| Windows 安装版 | 113 MB | 单文件安装包，带卸载 |

### 3.2 最值钱的一次重构：300 MB → 1.68 MB

第一版桌面端用 Electron 整包，300 MB。
后来改成 **1.7 MB 的 C# 启动器 + 系统自带 Edge/Chromium 内核**：

- 首次启动解压站点到用户目录，之后秒开
- 便携版不写注册表
- 安装版带快捷方式与卸载项，支持 `--silent`

**这一步才让"分发"变得可能**——300 MB 没人愿意下，113 MB 才勉强能接受。

### 3.3 构建链（四端一致）

```
场景定义 → gen_v2.py（生成动效数据）
        → build_library_data.js / gen_site_data.js（站点数据）
        → build_apk.sh（安卓）
        → build_desktop.sh（桌面，含自检）
        → pack_installer.py（安装包 + 便携版）
```

**自检是保命的**：构建结束会断言「便携版看不见管理员入口」「安装版看得见」，
对不上直接失败，不让带病产物出厂。

### 3.4 安装器与卸载（踩过的坑）

| 坑 | 现象 | 修法 |
|---|---|---|
| 尾标记字节数不一致 | 打包写 24 字节、安装器读 32，报「找不到路径」 | 固定 32 字节 + 打包后自检 magic/偏移/EOCD |
| 卸载删到自己 | 删到一半进程被杀 | 先把自身复制到临时目录再执行 |
| 卸载残留 | 注册表、启动项、快捷方式没清 | 逐项清理并弹报告 |
| 升级覆盖失败 | 检测到旧版就报「文件夹非空」 | 检测到已安装即按升级处理，数据目录保留 |

### 3.5 分发通道

| 阶段 | 通道 | 结论 |
|---|---|---|
| 早期 | 本机打包，微信/网盘发 | 简单，但无版本管理 |
| 中期 | GitHub 私有仓 + Release | 能存能下，但私有链接别人打不开 |
| 现在 | 公开仓 `Z-20user/Zingdex` | 任何人可下；46 个版本全部公开 |

**硬约束（实测）**：

- 仓库单文件 >100 MB 传不上去 → 安装包只能走 Release
- Release 单附件 ≤ 2 GB
- 本机 `github.com:443` 被重置 → `git push` 不通，改走 `api.github.com` 与 `uploads.github.com`
- 私有仓的下载链接对外无效，必须公开才谈得上"分享"

## 四、为什么放弃

四层原因，从表到里。

### 4.1 表层：决定免费

免费开放，所有人都能用，授权层就没有意义了。

### 4.2 技术层：它本来就挡不住

- 纯前端，改本地状态即可绕过
- APK 内含明文码，解包即得
- 想做真防护必须上服务端（账号、设备绑定、签发令牌）

### 4.3 产品层：它让第一次体验变重

用户打开软件，第一眼看到的是「等级 / 激活码 / 令牌」，
而不是「这东西能帮我干什么」。

**入口的门槛，比内容的价值先被感知**——这是最伤的一点。

### 4.4 运营层：一个人做不过来

- 收费要有主体（个体户/公司）、要对公、要开票
- 上架商店要软著 + 备案 + 审核
- 推广要渠道、要内容、要持续更新
- 出了问题要客服

> 开发占三成，运营与支持占七成。一个人可以扛住前者，扛不住后者。

### 4.5 一句话结论

**在还没有用户的阶段投入授权体系，是把顺序做反了。**
先让人用起来，再谈收钱；先证明有人要，再建闸门。

## 五、如果重来，会怎么做

按顺序，每条都是今天的我会做的选择：

| 顺序 | 动作 | 为什么 |
|---|---|---|
| 1 | 先免费发布，收集真实使用 | 先验证需求 |
| 2 | 只做「一次买断」或「赞助」，不做分级 | 分级只对 To B 有意义 |
| 3 | 授权校验**只在需要时**加，默认无 | 别让闸门挡在入口 |
| 4 | 真要防破解，先上服务端 | 纯前端不要自欺 |
| 5 | 多端里只做「装得下、下得动」的形态 | 体积是第一道门槛 |
| 6 | 把构建与发版自动化，人工只做决策 | 一个人的时间是唯一稀缺资源 |

## 六、留下的可复用资产

放弃的是"收钱的闸门"，不是代码。这些值得留着：

| 资产 | 在哪 | 价值 |
|---|---|---|
| 令牌 Ed25519 验签（主进程） | `_废弃_授权机制/` | 任何需要离线签名的场景都能用 |
| 安装器（自包含、静默安装、卸载报告） | `03_源代码/tools/` | 换成任何产品都能复用 |
| 四端构建链与自检 | `build_*.sh`、`pack_installer.py` | 保证多端一致 |
| 数据生成管线 | `gen_v2.py` 等 | 内容与代码分离的范式 |
| 动效库本身 | `04_动效代码库/` | 20,000 条，与授权无关 |

## 七、给未来的自己（重做时的检查清单）

- [ ] 先确认「有人要用」，再动手做收费
- [ ] 首次打开三秒内能看到价值，不要放授权墙
- [ ] 如果一定要授权：服务端裁决，客户端只做展示
- [ ] 任何加密方案先做「故障注入测试」（密码错、换机、断网）
- [ ] 令牌不要绑定文件指纹，否则升级即失效
- [ ] 体积目标：安装包 ≤150 MB，APK ≤5 MB
- [ ] 构建自检写死关键断言，不让带病版本出厂
- [ ] 发版必须写一行变更记录（本次 2.x 就漏了，导致回溯困难）
- [ ] 分发通道先想清楚：私有只能自用，公开才能分享
- [ ] 时间分配：开发 30%，运营 50%，支持 20%——按这个排期，不然一定崩

## 八、结语

这套授权体系花了不少工夫，也确实是"能跑起来"的：
令牌能验、等级能升、密钥能发、安装包能装能卸。

放弃它的原因不是它坏了，而是它所服务的那个目标——先收费——不成立。

把这段记录下来，是因为下一次再想做"收费版"的时候，
最容易忘记的恰恰是这一条：**先有人用，再谈怎么收钱。**
