## 一、这份报告在说什么

本报告记录三件事：

1. 这套软件是怎么被造出来的——从数据生成到四端打包到每次发布前的验证；
2. 反编译与反破解在这套纯前端架构里做到了什么程度、边界在哪、怎么验证的；
3. 如果将来接后端服务器做成真正可广泛传播的商用产品，防护体系应该怎么设计。

同时附上四个版本的最终核查结果。

## 二、产品形态：已经是一套完整的生态

这套东西不是"一个软件"，而是**四个端 + 两条数据链**构成的一套生态。

### 2.1 四个端

| 端 | 形态 | 定位 | 权限上限 |
|---|---|---|---|
| 电脑安装版 | Electron 自解压安装包（111.8 MB） | 开发主力 | S 级令牌（管理员 / 可开发模式） |
| 电脑便携版 | 免安装文件夹（180 MB） | 展示、试用 | S 级激活码 |
| 手机动效版 | Android APK（2.1 MB） | 移动展示、引流 | S 级激活码 |
| 手机密钥版 | Android APK（0.4 MB） | 管理员随身密钥本 | 不涉及（仅保管码） |

外加一个 Windows 端**离线密钥库**，用于在电脑上加密保管密钥总表。

### 2.2 两条数据链

**内容链**：场景定义 → 生成器 → catalog.json（4000 条）→ 分片库（120 个 JS 分片）→ 四端共用。

**授权链**：明文密钥表 → 构建脚本 → 哈希表（客户端只存哈希）→ 各端激活校验。

两条链同源，所以四端看到的数量、名称、参数永远一致——这是靠"单一数据源 + 确定性构建"保证的，不是靠人工对齐。

## 三、开发流程

### 3.1 总体流水线

```
场景定义（120 个场景元组）
   ↓  gen_v2.py（确定性生成，无随机数）
catalog.json（4000 条动效，18 MB）
   ↓  build_library_data.js
site/assets/lib/*.js（120 个分片，10.5 MB，按需加载）
   ↓  gen_site_data.js
site/assets/data.js（224 KB，场景索引）
   ↓
┌──────────────┬──────────────┬──────────────┐
Electron 打包    Android 打包    密钥 App 打包
   ↓              ↓              ↓
安装包 + 便携版   动效 APK        密钥 APK
```

### 3.2 关键工程决策

**一、确定性构建。** 生成器里没有随机数。同样的输入必然产出同样的字节，产物可以逐字节复现。这一条让"我本地是好的，你那边不对"这类问题基本消失。

**二、构建后自检。** 每次构建结束自动跑一遍：组件数量、页面标题、形态分组、代码复制、PDF 导出、全屏行为、激活流程、**权限分层**（便携版看不见管理员入口、安装版看得见）。任一项不通过，构建直接失败，产不出包。

**三、安装与卸载实测。** 每次发布前在干净目录跑一遍完整回归：装 → 运行产生数据 → 覆盖升级 → 核对数据仍在 → 卸载 → 核对安装目录、`%APPDATA%`、`%LOCALAPPDATA%`、卸载登记、开机启动、程序注册键全部清空。

**四、安装器自包含。** 安装包是"PE 启动器 + 尾部数据包"的单文件结构，尾部有 32 字节标记（magic + 偏移 + 长度 + 保留位）。打包器写完会自检这个标记，读不到就报错，不会产出一个"看起来能装、装到一半报错"的包。

**五、卸载器自复制。** 卸载程序先把自己复制到临时目录再执行，避免"删到一半把自己删掉"。每一步在进度条上回报，完成后弹出逐项报告，并在桌面留一份残留检查脚本。

### 3.3 踩过的坑（有代表性的）

| 现象 | 根因 | 修法 |
|---|---|---|
| 安装包装到一半报"找不到路径" | 尾标记写了 24 字节，安装器按 32 字节读 | 固定 32 字节 + 打包后自检 |
| 卸载什么都没删 | 临时副本丢了 `--uninstall` 参数，被当成安装程序 | 子进程参数补上 |
| 密钥 App 版本号连发三版都改不动 | manifest 硬写了 versionCode/versionName，aapt2 的 `--version-*` 只在缺省时生效 | 构建前 sed 改写清单副本 + 构建末尾断言版本号 |
| 皮肤点了没反应 | CSS 写 `.skin.is-on`，JS 加 `on` 类 | 统一类名 |
| 卡片动效"静止"无效 | `dataset.cardAnim` 实际写的是 `data-card-anim`，选择器对不上 | 改选择器 |
| 手机"跟随系统"变深色 | WebView 的 `prefers-color-scheme` 跟的是应用主题，不是手机设置 | 改以原生 `systemDark()` 为准 |
| 设置页改了没生效 | 静态资源 `?v=` 没升，浏览器吃旧缓存 | 每次改样式同步升版本号 |

这些坑有一个共同点：**都是"看起来对但实际没接上"**。所以后来养成了两个习惯——改完立刻在真机/真窗口里验证；凡是能自动断言的，就写进构建脚本，不靠人记。

## 四、反编译与反破解：做到了什么，边界在哪

先把结论放在前面：

> **在纯前端、无后端的架构下，任何客户端防护都只能提高成本，不能提供保证。**
> 真正守得住的东西只有两样：**不放进客户端的秘密**，和**服务端的裁决权**。
> 而这套产品两样都没有——它就是故意的。

### 4.1 已经做的（按层次）

**第一层：把秘密从客户端拿掉**

| 措施 | 实现 | 能挡住什么 |
|---|---|---|
| 激活码只存哈希 | `keydata.js` 里只有 `sha256("transient.v2.keys\|"+码)` 的前 12 字节 base64 | 解包看不到任何一枚可用码 |
| 令牌用非对称签名 | 管理员令牌 Ed25519 签名，客户端只有公钥 | 伪造不了令牌；改了内容签名对不上 |
| 明文清单只在本地 | 密钥总表在 `04_密钥与授权`，不进任何安装包 | 分发物里没有秘密 |
| 内容与授权同源分离 | 组件数据与密钥哈希是两份文件 | 拿到内容不等于拿到授权 |

**第二层：按运行形态裁剪界面**

判断依据是主进程报上来的运行形态（`Uninstall.exe` 存在 = 安装版），不是任何前端变量。

```js
installedDesktop()  →  window.transient.modeSync === "installed"
portableNoAdmin()   →  !installedDesktop()
```

便携版与手机端连"管理员 / S 级令牌"的字样都不出现，令牌入口在代码层被删掉，不是隐藏。构建自检每次都会断言这一点。

**第三层：平台层加固**

| 端 | 措施 |
|---|---|
| Electron | `contextIsolation: true`、`nodeIntegration: false`、无应用菜单、屏蔽 F12 与 Ctrl/Cmd+Shift+I/J/C、`devtools-opened` 立即关闭、站外链接交给系统浏览器、拦截全部 http/https 请求 |
| Android | 不声明 `INTERNET` 权限（系统层面就无法联网）、minSdk 23、APK 签名、激活状态绑定 `ANDROID_ID` |

**第四层：行为约束**

- 密钥 App 里每枚激活码**只能复制或导出一次**，用过变灰；
- 复制前必须先过指纹/锁屏验证，再填去向与使用人；
- 使用统计只追加，App 内不提供任何清除入口；
- 切后台自动落锁。

这一层的意义不是防破解，而是**防误用与内部流失**——知道谁在什么时候取了哪一枚、发给了谁。

**第五层：工程约束**

- 构建后自检 + 安装回归，防止"发出去才发现装不上"；
- 数据全面脱敏，避免因内容本身引发权利争议；
- 文档里明确写出授权边界与禁止行为，并援引具体法条。

### 4.2 挡不住的（必须说清楚）

| 攻击方式 | 为什么挡不住 | 实际影响 |
|---|---|---|
| 改激活状态 | 激活状态存在本机（文件 / localStorage），改一下就是 S 级 | **这是最大的弱点**：能解锁无限次数 |
| 改哈希表 | `keydata.js` 是明文 JS，往里面加条目即可 | 可自造"有效码"，但只在本机有效 |
| 改前端逻辑 | 所有判定都在 JS 里 | 可以绕过任何 UI 层限制 |
| 重打包 | 换签名重新打包即可分发 | 传播不受控（但激活仍需码） |
| 抓取内容 | 组件数据本来就是给用户看的 | 无影响——内容不是秘密 |

**关键结论：** 这套防护实际上防的是"随手解包看一眼"和"内部流失"，防不住"有动机、有时间的人"。它守的是**合规与秩序**，不是**技术壁垒**。

### 4.3 怎么验证这些措施真的生效

不靠"我觉得"，靠可执行的检查：

```bash
# 1. 包里有没有明文码
python -c "import zipfile,re; z=zipfile.ZipFile('密钥.apk');
print(len(re.findall(r'TZ-[A-Z0-9]{5}', z.read('assets/keyapp/data.js').decode())))"

# 2. 便携版有没有管理员入口（构建自检里自动断言）
#    adminUi: { blockHidden: true, tierHidden: true, licInputVisible: false }

# 3. 安装版有没有开放管理员
#    appMode: "installed"  adminUi: { blockHidden: false, licInputVisible: true }

# 4. 升级不丢数据
#    装 → 跑 → 覆盖升级 → 探针文件仍在

# 5. 卸载不残留
#    安装目录 / APPDATA / LOCALAPPDATA / 卸载登记 / 开机启动 / 程序键 全 False
```

这五项每一轮发布都跑，结果写进构建日志。

## 五、这次尝试的结论

**做得对的地方：**

- 把"秘密不进客户端"当成了原则：激活码只存哈希，令牌用签名，明文清单不随包分发。这是纯前端架构下唯一真正有效的防线。
- 权限按运行形态裁剪，并且**构建时自动断言**——不靠人记得。
- 工程约束（自检 + 回归）比加密手段更能保证交付质量。
- 承认边界。没有假装自己防住了什么。

**做得过头的地方：**

- 密钥 App 一开始被做成了"本地口令 + PBKDF2 + AES + Keystore 记住"的加密保险箱。实践证明这是过度设计：一个全程离线、只给管理员自己用、价值有限的工具，加密带来的麻烦远大于收益，最后还因为解密链路让用户密钥显示为 0。
- 已回退为明文 + 连续编号（00001–10000 用户码，10001–11000 S 级码）。

**一句话总结：** 在没有服务端的情况下，**加密是表演，工程是实质**。这一轮真正的收获不是"防住了谁"，而是把构建、验证、脱敏、权限分层这套流程跑通了——这套流程才是接上后端之后能继续用的东西。

## 六、如果将来接后端服务器，防护应该怎么做

这是本报告最重要的一节。前提假设：产品要广泛传播、要有商业价值、要能持续运营。

### 6.1 根本前提：把裁决权放到服务端

纯前端架构的根本问题不是"加密不够强"，而是**客户端拥有最终裁决权**。

只要"这枚码有效吗""这个用户是几级""今天还能用几次"这三个问题的答案在客户端能算出来，防护就是纸糊的。

**所以第一原则是：客户端只负责展示和请求，不负责判定。**

| 原来在客户端 | 应该搬到服务端 |
|---|---|
| 码是否存在（哈希比对） | 码的校验与绑定 |
| 等级判定 | 等级存在服务端，随 token 下发 |
| 剩余额度 | 服务端计数，客户端只读展示 |
| 管理员权限 | 服务端签发短时 token |
| 内容是否可访问 | 服务端按权限下发内容 |

### 6.2 授权体系设计

**激活流程**

```
客户端：输入激活码 → TLS 请求 /activate（附设备指纹）
服务端：查码 → 校验未被使用 / 未被吊销 → 绑定设备 → 签发 token
客户端：安全存储 token，之后每次请求带上
```

要点：

- **设备绑定**：一个码绑定 1–2 台设备，超出需人工解绑；
- **token 短时效**：访问 token 15–30 分钟，刷新 token 7–30 天；
- **服务端可吊销**：发现泄露立刻在服务端作废该码，客户端下次请求即失效。

**等级与额度**

等级、每日额度、并发设备数**只存在于服务端数据库**，客户端拿到的 token 里只有"你是谁、什么等级、到期时间"，且每次请求服务端再校验一次。

额度用 Redis 做滑动窗口计数，客户端传什么都无关紧要。

**管理员模式**

管理员权限不应该是一个"本地开关"，而应该是：

1. 服务端签发**独立的、更短时效**的 admin token（比如 30 分钟）；
2. 每次进入开发接口都要重新校验；
3. 服务端记录每一次开发接口的调用（谁、什么时候、做了什么）；
4. 支持远程立即失效。

这就是现在安装版"会话级管理员模式"的服务端版本——现在靠"退出进程即失效"，将来靠"token 过期即失效"。

### 6.3 内容保护

组件数据的价值不在"保密"，在于"授权范围内的使用"。所以：

- **免费层**：给完整的少量样例（比如 5%），足够展示能力；
- **付费层**：按套餐下发内容分片，客户端本地缓存，缓存有 TTL；
- **服务端水印**：每次下发的内容里嵌入该用户的不可见标识（顺序、命名、参数微扰），一旦外流可以溯源到具体账号；
- **不追求"无法复制"**：只要内容被下发到客户端，就能被抓。追求的是"可溯源 + 可吊销"。

### 6.4 传输与客户端加固

| 层 | 措施 |
|---|---|
| 传输 | 强制 TLS 1.3；证书固定（pinning）防止中间人 |
| 客户端 | 关键逻辑混淆（不是加密）；反调试；完整性自校验（签名哈希比对） |
| 分发 | 服务端校验客户端上报的签名证书哈希，非官方签名直接拒绝服务 |
| 更新 | 灰度发布 + 强制更新开关 + 旧版本降级限制 |

**注意：** 客户端加固永远只是"提高成本"。把资源投在服务端风控上，回报远高于客户端混淆。

### 6.5 风控与运营

真正防住滥用的往往不是技术，是运营手段：

- **异常行为检测**：同一码短时间内多地登录、同一设备频繁切换账号、额度消耗曲线异常 → 自动冻结 + 人工复核；
- **分级响应**：轻度异常限速，中度异常要求重新验证，重度异常直接吊销；
- **黑名单**：已知的破解包签名、已知的代理 IP 段；
- **审计日志**：每一次授权判定都留痕，出事能查。

### 6.6 离线场景怎么折中

完全离线就没法服务端裁决。折中方案：

1. 首次激活必须联网，拿到一个**有时效的离线许可证**（比如 30 天）；
2. 许可证用服务端私钥签名，客户端用公钥验签（和现在令牌的做法一样，但由服务端签发）；
3. 到期必须联网续期；
4. 服务端可以下发**吊销列表**，客户端联网时同步。

这样离线可用，但控制权仍在服务端。

### 6.7 成本与收益的现实判断

| 阶段 | 建议投入 |
|---|---|
| 小众分享（现在） | 不做服务端。工程约束 + 数据脱敏 + 明确的法律文本，足够了 |
| 开始收费 | 上服务端：激活校验 + token + 额度计数。这一步是分水岭 |
| 规模化 | 加风控、水印、分级响应、审计 |
| 企业客户 | 私有化部署 + 离线许可证 + 合同约束 |

**最重要的一条建议：** 不要在纯前端阶段继续加码客户端加密。投入产出比极低，而且会像这次一样，为了"安全"牺牲可用性，最后还得回退。**把力气留到接后端的那一天。**

## 八、维护指引

### 8.1 日常迭代

```
改代码 → node --check 语法自检 → 构建（自动跑自检）
      → 安装回归 → 部署到交付位 → adb 装机验证 → 记版本
```

### 8.2 版本号规则

| 产品 | 规则 |
|---|---|
| 动效组件库 | `1.12.x`（三段式），Android versionCode 每次 +1 |
| 瞬态密钥 | `0.0.x.y.zwb`，versionCode 每次 +1 |
| 离线密钥库 | `0.0.0.0.zwb` 起 |

### 8.3 三端升级方式

| 版本 | 方式 |
|---|---|
| 手机版 | 直接装新 APK 覆盖，数据保留 |
| 便携版 | 新文件夹整体替换；保留数据的做法是先把 `data` 拷出，替换后再放回 |
| 安装版 | 直接双击新安装包装到原路径，会自动结束运行中的进程，`data` 原样保留，不需要先卸载 |

### 8.4 不要动的东西

- `04_密钥与授权` 下的明文清单——这是唯一的真源，丢了就得重新生成；
- 每端的签名证书（keystore）——换了签名，覆盖安装会失败；
- `app_version.py` / `version.txt` 的对应关系——两处必须同步，否则文件版本与界面版本会对不上。
