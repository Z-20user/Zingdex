# 商业化触发条件 / Commercialization Triggers

**当前结论：不收费，且没有近期收费计划。**

这份文档的作用不是「准备收费」，而是**把什么时候才会重新考虑写死**，
免得将来凭感觉做决定，或者被一句「要不加点付费功能」就带偏。

---

## 一、不做什么（现在就定死）

| 不做 | 原因 |
|---|---|
| 付费墙 | 入口放门槛，是 2.x 已经犯过的错，见 `AUTHORIZATION-RETROSPECTIVE.md` |
| 分级会员 | 单人维护，没有客服能力支撑分级 |
| 卖数据包 | 数据已经 CC BY 4.0 公开，再卖是自欺 |
| 把已有功能改成付费 | 破坏信任，且不可逆 |
| 在应用里加广告 | 与「完全离线、不联网」的设计直接冲突 |

**开源的承诺不因商业化而改变。** 已经发布的版本永远是 Apache-2.0 / CC BY 4.0。

---

## 二、什么情况下才重新考虑

必须**同时**满足下面三条中的至少两条，才会启动讨论：

### 触发条件 A：支持成本超过可承受范围

- 每月 Issue + 邮件 + 讨论区的问题量 > 50 条
- 其中 > 30% 是「怎么用」而非「有 bug」
- 意味着需要每周末投入半天以上做支持

→ 可能的解法：**优先做文档和示例，而不是收费**。收费不减少支持量。

### 触发条件 B：出现明确的企业需求

- 有 3 家以上公司明确提出同一类需求（例如：私有化部署、定制动效规范、SLA）
- 且愿意为此付费（有预算确认，不只是口头说想要）

→ 可能的解法：**做定制服务，不做产品分级**。卖时间比卖许可更诚实。

### 触发条件 C：维护成本压过收益

- 连续 3 个月，每周用于维护的时间 > 8 小时
- 且没有新的贡献者接手

→ 可能的解法：**降低维护强度**（放慢发版、冻结新功能），而不是收费。

---

## 三、如果真的要收钱，按这个顺序

1. **赞助 / 打赏**（GitHub Sponsors）—— 不改变任何功能，愿者上钩
2. **定制服务** —— 按项目报价，交付私有定制，不碰开源部分
3. **企业支持合同** —— 响应时限 + 优先修 bug，代码仍然开源
4. 最后才考虑产品分级 —— 且已有功能永不降级

前三条都不需要改代码。这是刻意的：**商业模式的变化不应该影响用户手里的东西。**

---

## 四、判断标准

做任何商业化决定前，先回答这三个问题：

| 问题 | 不合格的信号 |
|---|---|
| 这个改动会让现有用户少得到什么吗？ | 是 → 不做 |
| 它需要我额外提供服务（客服、对接、售后）吗？ | 是 → 先算清时间成本 |
| 停了它，项目还能正常运转吗？ | 不能 → 说明它绑定了核心，重做 |

---

## 五、承诺

写在这里，是为了将来有人（包括未来的我）想改的时候，必须先把这几行删掉：

- 已发布的版本永远保持 Apache-2.0 / CC BY 4.0
- 不会把现有免费功能改成付费
- 不会为收费而在应用里加账号、联网、埋点
- 如果哪天要变，会在 `CHANGELOG.md` 和 README 里提前一个月写明

---

## 六、现在靠什么运转

不靠钱。靠的是：

- 静态托管成本 ≈ 0（GitHub Releases + 仓库）
- 无服务器、无数据库、无第三方 API
- 构建在本机完成

这是这个项目能一个人长期维护的真正原因 —— **不是不想商业化，是成本结构不允许它变重。**
